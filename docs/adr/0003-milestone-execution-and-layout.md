# ADR-0003: التنفيذ بالمراحل وهيكل الحزم

**الحالة:** مقبول · **التاريخ:** 2026-10-08

## السياق

- خطة `docs/TASKS.md` القديمة كانت مهاماً متفرقة (T00–T22) ومراجعين (R1–R6)، ولا تسلّم ميزات كاملة يراها المستخدم في كل خطوة.
- المستخدم وضع ست قواعد ملزمة: مراحل بميزات كاملة في 2–4 ساعات؛ لا أهداف لعدد الأسطر؛ بنّاؤون متوازيون على حزم منفصلة يلتزمون بالعقود؛ مدققون مستقلون مع إصلاح في المكان وإعادة تدقيق؛ بوابة إغلاق (كل الاختبارات وبناء أندرويد وموافقة المدققين ثم commit و push)؛ ملف لكل مرحلة.
- البناء المتوازي يتطلب ملكية حصرية لكل ملف. في الهيكل السابق كانت ميزات التطبيق داخل `apps/mobile` وملفات النصوص مشتركة، فيتصادم البنّاؤون.
- المستخدم وافق على التنفيذ المستقل، والعمل كله على فرع واحد.

## القرار

**نموذج التنفيذ** (التفاصيل في [`docs/milestones/README.md`](../milestones/README.md)):

- ثماني مراحل M0–M7، لكل منها ملف في `docs/milestones/` يحدد الميزات والمعايير والوكلاء والتقدّم.
- كل مرحلة: فحص جاهزية، ثم تجميد العقود (المكامل وحده)، ثم بنّاؤون متوازيون كوكلاء في الخلفية على مسارات منفصلة، ثم تكامل، ثم مدققون مستقلون، ثم حلقة إصلاح (3 جولات كحد أقصى، ثم يقرر القائد)، ثم بوابة الإغلاق.
- كل العمل على `claude/iraq-smart-maps-app-aybpjn`. لا فروع أخرى ولا tags ولا GitHub Releases. الإغلاق: البوابة خضراء، ثم commit و push، ثم تسجيل الـ SHA في ملف المرحلة. ملف APK ومخرجات البيانات تُسلَّم كـ Actions artifacts.
- الملكية في front-matter ملف المرحلة وفي `tools/ownership/milestones/Mx.json`، ويفرضها `pnpm ownership:check`.
- كل اعتماد يحتاج مفتاحاً خارجياً يُستبدل بـ mock مسجّل في [`MOCKS.md`](../milestones/MOCKS.md).

**الهيكل:**

1. ميزات التطبيق حزم مستقلة `mobile-features/<x>` باسم `@iraq-maps/feature-<x>` (map، navigation، account، provider، messages، assistant، discover، activity؛ و tour3d بملف README فقط). كل حزمة تصدّر شاشاتها، وتملك نصوصها في `src/i18n/{ar,ckb,en}.json` كمساحة أسماء، وتدفقات Maestro الخاصة بها. الميزات لا تستورد بعضها، وتتنقل عبر روابط typed في `mobile-kit` وتخفي الأزرار بـ `useRouteAvailable`.
2. `apps/mobile` رفيع: ملفات الإعداد الجذرية، و `app/**` كسطور re-export، و `src/shell/**` (منها `available-routes.ts` وشاشة «إعدادات المطوّر» في النسخ غير الإنتاجية).
3. حزم مشتركة جديدة: `packages/mobile-kit`، و `packages/map-kit`، و `packages/testing` (fakes و conformance suites، يملكها المكامل)، و `packages/observability`.
4. محوّلات الخدمات الخارجية في `adapters/<name>` باسم `@iraq-maps/adapter-<name>`، كل محوّل ينفّذ منفذاً واحداً ويستورد `packages/contracts` و `packages/config` فقط.
5. قواعد dependency-cruiser إضافية: `adapters/*` ← `packages/*` فقط؛ `modules/*` لا تستورد `adapters/*`؛ `mobile-features/*` ← `packages/*` فقط؛ `apps/api` ← `modules/*` و `adapters/*` و `packages/*`.
6. أدوات عليا: `e2e/api`، و `e2e/mobile`، و `tools/ownership`، و `tools/bench`، و `tools/assistant-evals`. ومشاريع `geo-services/*` لها `package.json` رفيع لتدخل `pnpm turbo run test`.
7. `docs/TASKS.md` يصبح مؤشراً مستبدَلاً، ومراجعوه R1–R6 يصبحون عدسات التدقيق.

## البدائل المرفوضة

- **الإبقاء على المهام T00–T22:** لا تسلّم ميزات كاملة في كل خطوة، وتخالف القاعدة الأولى.
- **ميزات التطبيق داخل `apps/mobile/src/features`:** ملكية مختلطة للنصوص والمسارات، وتعارضات بين البنّائين المتوازيين.
- **فرع لكل مرحلة مع PR و tag:** مرفوض بقرار القائد؛ فرع واحد يكفي ويبسّط قراءة CI.
- **عدّ الأسطر كمقياس للجودة:** مخالف للقاعدة الثانية؛ يُستبدل بـ `knip` و `jscpd`.

## العواقب

- البنّاؤون يعملون بالتوازي بلا تعارض إلا في `pnpm-lock.yaml`، ويُعاد توليده بـ `pnpm install`.
- تجميد العقود قبل البناء يجعل أي نقص فيه مكلفاً (طلب تعديل عقد ثم تجميد صغير).
- المكامل يحدّث §3 في `docs/ARCHITECTURE.md` و `CLAUDE.md` ليطابقا هذا الهيكل.
- حزم أكثر في الـ workspace، مقابل حدود واضحة تفرضها الأدوات آلياً.
